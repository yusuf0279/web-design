# Web Design Expedition

Help the agent make interfaces that feel intentional and specific to their product, audience, and task—and visibly unlike the agent’s recent website work. Research the design landscape, identify both conventions and open space, audit prior designs for repetition, explore structurally different directions, draw the plan, then build and inspect the real experience. A new palette or content swap does not make a reused layout original. Do not jump from a vague prompt to a generic page template.

Read [the web design expedition](references/design-pipeline.md) for the workflow and its checkpoints. For substantial work, preserve decisions and evidence in [the design run record](references/design-run-template.md).

Show the user visual progress whenever it is useful and feasible: a board of reference screenshots, a pattern map, distinct design territories, palette swatches, wireframes, and rendered screenshots. Prefer openable visual artifacts to prose-only descriptions. Do not make the user wait for a preview when they have asked you to work autonomously: show it, state the choice, and continue. For exploratory work, pause at the direction or wireframe checkpoint for a choice when that choice could materially change the result.

Use the connected screenshot/design corpus when available, including Lazyweb MCP. Extend corpus findings with live website research and browser inspection when useful. Read [the inspiration corpus](references/inspiration-corpus.md) for cross-sector visual galleries and UX-flow libraries. Choose sources according to the design question; do not treat the list as a requirement to inspect every gallery on every task. If a source, capture, or visual tool is unavailable, use the best available route and identify what was not verified. Keep counts tied to the inspected sample; never turn a small sample into a universal rule.

Use this workflow as the design authority for the task. Do not route the work through other design skills, template generators, UI kits, or preset component systems as a substitute for the research and decisions here. Existing product components may be reused when they fit and their use is intentional. Treat familiar SaaS patterns as hypotheses to test, not defaults to copy.

Hard requirements: never use status bubbles, status pills, badge-shaped status labels, or status dots anywhere in the interface. Never deliver a website as a single page: create a homepage plus multiple distinct, useful routes, selected from the product and sector research. Never collapse separate app tasks into one screen. Research the same product category before deciding route structure or visual direction. Choose colors through the evidence-led [palette picker](references/palette-picker.md). Define a role-based color system and compact type scale in the design contract. For substantial public websites, use researched, rights-cleared real imagery in the opening experience and at least one additional useful placement; only omit the additional placement after a focused search and a recorded product-specific reason. **The hero is never exempt: every homepage and every top-level route hero must carry a visual hook that is visible in the first viewport, on desktop and mobile: a real image, a video, an animation, or a purposeful graphic (a code-native or first-party-capture product visual counts; a text-only hero does not).** Pick the strongest option the product supports, make it relevant to what the product actually does, and never fake data or screenshots that show real private information. Give pages tactile motion: entrances, reveals and interactive controls use spring physics (Motion springs, or a CSS `linear()` spring curve) tuned to settle quickly without wobble, with a static state under `prefers-reduced-motion`. Do not generate raster images with AI or use unverified assets. If an asset-generation capability is unavailable or produces unusable output, continue with verified existing or licensed assets, first-party captures, code-native diagrams, or a purposeful image-free composition; record the limitation and never leave a broken or generic placeholder. **Favicon is part of every design pass, not only redesigns: whenever colours, logo or style change, regenerate `/favicon.ico` (multi-size ICO, 16/32/48/64) plus the SVG/apple icon from the site's real mark in its exact brand colours, and check it at 16px and 32px before delivery. A stale, starter or off-palette favicon, or a 404 on `/favicon.ico`, is a failed delivery; `scripts/visual_gate.mjs` fails on it.** Read the asset and favicon fallback procedure in the design pipeline. Keep ordinary text readable at real viewport sizes: at least 16px for body text, 14px for supporting text, and 12px only for brief metadata.

**Every finished website or web app built under this skill must be a Next.js application.** For an existing Next.js project, work within its established architecture and conventions. For a new project or a non-Next.js website being redesigned, create or migrate it to Next.js, normally using the App Router and TypeScript. Implement every planned page as a real route and use React components/layouts for shared structure. Do not deliver the production site as raw standalone HTML, CSS, and JavaScript, a static file bundle, or another framework. Low-fidelity wireframes and design boards may use HTML/CSS or SVG as preview artifacts, but they are not the website implementation. Use the project's existing package manager and scripts; if creating a new app, provide the normal Next.js development and production build scripts and required metadata/assets.

Read [visual exclusions and composition checks](references/anti-slop-design.md) on every substantial design. It rules out common agent-generated treatments including tiny hero eyebrows, italic serif fragments in hero headlines, arbitrary purple gradients, sparkle/emoji decoration, glassmorphism, cloned card grids, card-side stripes, numbered rows with dividers, decorative monospace, inconsistent type/spacing/grid alignment, translucent or jittery headers, overloaded heroes, glowing hover effects, dead controls, missing loading feedback, and incomplete metadata. It also checks truthful copy/analytics, meaningful licensed imagery, and purposeful motion, including Motion from motion.dev where it fits. For gesture-driven or motion-critical interfaces, apply the relevant fluid-interaction principles there: immediate feedback, direct manipulation, interruptible movement, and continuity into momentum. These are interaction techniques, not a mandate to imitate Apple's visual style; Web Design's product research and explicit visual exclusions remain in force. Apply checks to the plan and rendered pages; treat exceptions as product decisions that need evidence, not decoration preferences. Inspect every route at real viewport sizes.

The workflow is complete when the implementation has been inspected at real sizes, important interactions work, visual failures have been corrected, repetition against prior work has been checked, and actual evidence and limitations are reported. Do not call a build passing equivalent to visual review. Never claim to have inspected screenshots that were not captured and viewed. Do not publish or deploy unless requested.

Overlap and sameness are hard failures. Content boxes must not overlap unless the overlap is a documented, composed decision marked `data-overlap="intentional"`; run `scripts/visual_gate.mjs`, which reports every other overlap. A product visual never sits on top of a photograph. Also reject the templated tells listed under "Does not look templated" in the anti-slop reference: one hero skeleton reused everywhere, label + H2 + cards on every section, a default header, and pages that could belong to any product.
